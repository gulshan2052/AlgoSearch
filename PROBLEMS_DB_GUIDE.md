# Inserting Scraped Problems into `problems.db`

This document defines the database schema and the exact format required to insert
competitive-programming problems into the SQLite database so that the AlgoSearch
pipeline can pick them up and process them.

## Overview

The application uses two stores:

1. **SQLite database** (`problems.db`) – stores the raw problem metadata and text.
2. **ChromaDB vector store** (`data/chroma`) – stores embeddings for search.

Your job is to write newly scraped problems **only into the SQLite database** with
status `PENDING`. The application's ingestion pipeline will:

1. Select problems with status `PENDING`.
2. Call an LLM to produce a canonical algorithmic summary.
3. Generate an embedding and store it in ChromaDB.
4. Set status to `COMPLETED`.

Any problems left with status `PENDING` will be picked up on the next ingestion run.
Statuses other than `PENDING` are managed by the pipeline itself and should NOT be
written by the scraper.

## Database Location & URL

- The scraper MUST **not** write to the project's `problems.db`. It writes freshly
  scraped problems to its own separately named file, e.g. `new_problems.db`.
- File format: SQLite at the project root (relative), SQLAlchemy URL
  `sqlite:///./new_problems.db`.

> To load a scraped file into the catalog, copy `new_problems.db` into the import
> directory `data/imports/` and call the import endpoint:
>
> ```bash
> curl -X POST "http://localhost:8000/api/v1/problems/import"
> #  or, to import one specific file:
> curl -X POST "http://localhost:8000/api/v1/problems/import?filename=new_problems.db"
> ```
>
> The endpoint merges every row into the existing `problems.db`, keyed on the unique
> `url` column, so already-present problems are skipped and existing data is never
> overwritten. Imported files are never modified or deleted, so they can be
> re-imported safely as often as needed. Chroma data is NOT part of your job; it is
> generated by the ingestion pipeline.
>
> The catalog's `problems.db` (SQLAlchemy URL `sqlite:///./problems.db`) is created
> automatically on first application boot if it does not exist
> (`app/db/session.py` → `init_db()`). Do not write to it directly.

## Table Schema

Only one table (`problems`) needs to be created/populated.

### `problems` table – column layout

| Column           | Type            | Nullable | Default                          | Notes                                                    |
|------------------|-----------------|----------|----------------------------------|----------------------------------------------------------|
| `id`             | INTEGER         | NO (PK)  | autoincrement                    | Primary key, auto-generated. Do not set.                 |
| `platform`       | VARCHAR(50)     | NO       | –                                | Source platform, e.g. `codeforces`, `leetcode`, `cses`.  |
| `problem_id`     | VARCHAR(100)    | NO       | –                                | Platform's own slug/id, e.g. `158A`, `two-sum`.          |
| `title`          | VARCHAR(255)    | NO       | –                                | Display title of the problem.                            |
| `url`            | VARCHAR(500)    | NO       | –                                | Canonical URL. **Must be globally unique.**              |
| `statement`      | TEXT            | NO       | –                                | Raw full problem text (see format below).                |
| `constraints`    | TEXT            | YES      | NULL                             | Raw constraints section text. NULL if not applicable.    |
| `input_format`   | TEXT            | YES      | NULL                             | Input spec section text. NULL if not applicable.         |
| `output_format`  | TEXT            | YES      | NULL                             | Output spec section text. NULL if not applicable.        |
| `status`         | ENUM           | NO       | `PENDING`                        | One of `PENDING`, `PROCESSING`, `COMPLETED`, `FAILED`.   |
| `summary`        | TEXT            | YES      | NULL                             | LLM summary. Always NULL for new rows.                   |
| `error_message`  | TEXT            | YES      | NULL                             | Failure detail. Always NULL for new rows.                |
| `created_at`     | DATETIME        | NO       | current timestamp (UTC)          | ISO 8601 UTC timestamp when the row is written.          |
| `updated_at`     | DATETIME        | NO       | current timestamp (UTC)          | Same as `created_at` for new rows.                       |

### Reference DDL

```sql
CREATE TABLE problems (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    platform     VARCHAR(50)  NOT NULL,
    problem_id   VARCHAR(100) NOT NULL,
    title        VARCHAR(255) NOT NULL,
    url          VARCHAR(500) NOT NULL UNIQUE,
    statement    TEXT         NOT NULL,
    constraints  TEXT,
    input_format TEXT,
    output_format TEXT,
    status       VARCHAR      NOT NULL,
    summary      TEXT,
    error_message TEXT,
    created_at   DATETIME     NOT NULL,
    updated_at   DATETIME     NOT NULL
);

CREATE INDEX ix_problems_platform   ON problems (platform);
CREATE INDEX ix_problems_problem_id ON problems (problem_id);
CREATE INDEX ix_problems_status     ON problems (status);
```

> `status` is stored as a string in SQLite (SQLAlchemy `Enum`). Valid values are
> exactly the uppercase strings: `PENDING`, `PROCESSING`, `COMPLETED`, `FAILED`.

### Status enum

| Value        | Meaning                                                              | Written by |
|--------------|----------------------------------------------------------------------|------------|
| `PENDING`    | Scraped, awaiting ingestion.                                         | Scraper    |
| `PROCESSING` | Ingestion in progress.                                               | Pipeline   |
| `COMPLETED`  | Summarized, embedded, indexed in ChromaDB.                           | Pipeline   |
| `FAILED`     | Ingestion failed; `error_message` holds the reason.                  | Pipeline   |

## Insert Rules for New Scraped Problems

A row is inserted with:

- `status = 'PENDING'`
- `summary = NULL`
- `error_message = NULL`

### Required fields (must be non-empty)

- **platform** – normalized lowercase identifier of the source site
  (e.g. `codeforces`, `leetcode`, `cses`, `atcoder`, `codechef`, `spoj`).
- **problem_id** – the exact identifier used by the platform in URLs/feeds
  (e.g. `158A`, `two-sum`, `1097A`). Do not prefix with the platform name.
- **title** – the problem's human-readable title (may contain spaces).
- **url** – full absolute URL (e.g. `https://codeforces.com/problemset/problem/158/A`).
  This value **must be unique across the whole table**; skip/replace rows whose URL
  already exists to avoid duplicate-key errors.
- **statement** – the complete raw problem text.

### Optional fields

- **constraints** – the raw constraints section as text. Use `NULL` when a
  problem has no separate constraints section.
- **input_format** – raw input specification. `NULL` if none.
- **output_format** – raw output specification. `NULL` if none.

### `statement` content format

`statement` holds the **raw narrative text** scraped from the page. The pipeline
expects the *flavor/prose* portion as it appears on the site:

- Include the story/setting paragraphs, definitions, and the formal task.
- **Do NOT** include input/output format, constraints, or samples in `statement`
  if those are separate sections on the page – the purpose of this field is the raw
  description of the problem itself.
- Keep whitespace/newlines as-is (normalize CRLF → LF only).
- Strip HTML tags; keep plain text.

### `id`, `created_at`, `updated_at`

- `id` – let SQLite auto-assign it. Never supply it manually.
- `created_at` / `updated_at` – set both to the current UTC timestamp
  (`YYYY-MM-DD HH:MM:SS`). The pipeline relies on them only for ordering, but they
  must be present and non-null.

## Example INSERT

```sql
INSERT INTO problems (
    platform, problem_id, title, url, statement, constraints,
    input_format, output_format, status, summary, error_message,
    created_at, updated_at
) VALUES (
    'codeforces', '158A', 'Next Round',
    'https://codeforces.com/problemset/problem/158/A',
    'The contestant who solves at least "k" problems advances to the next round...',
    '1 <= n <= 50, 1 <= k <= n, 1 <= a_i <= 100',  -- or NULL
    'The first line contains two integers n and k...',
    'Print a single integer — the number of participants who advance.',
    'PENDING', NULL, NULL,
    '2026-09-05 10:00:00', '2026-09-05 10:00:00'
);
```

## Summary of Requirements

1. Create/populate a single SQLite table `problems` with exactly the columns above.
2. Set status `PENDING`, summary and error_message `NULL`.
3. Populate platform, problem_id, title, url, statement (required); constraints,
   input_format, output_format (optional, use NULL).
4. Enforce URL uniqueness; skip problems already present in the table.
5. Never write PROCESSING/COMPLETED/FAILED statuses or summary values.
6. Write the scraped data to a separately named file (e.g. `new_problems.db`),
   never to the project's `problems.db`. Copy the file into the import directory
   `data/imports/` and call `POST /api/v1/problems/import` to merge its rows into
   the catalog.
